Why

I learned backend with Express. In Java, the default hides a lot.

  • Express: a route is one line and a server is ten.
  • Spring Boot: powerful, but annotations, dependency injection and auto-configuration hide the machinery.
  • Question: what would a Java framework look like if it felt like Express?
  • To hide nothing I started at the lowest level: a ServerSocket and my own HTTP parser (v0.1.0).
  • A review of v0.1 found 15 real problems, so I rewrote it as a multi-module library and closed each one.

Principles

Rules that keep it small and safe

  • Zero runtime dependencies in jolt-core: the JDK only. Integrations live in optional modules.
  • Secure by default: every limit is on out of the box; risky features (CORS, metrics, static files, MCP, TLS) are opt-in.
  • Small, Express-shaped API: a new public method needs an ADR.
  • No silent failure: every request gets a response. A handler exception becomes a 500, never a hung connection.
  • Every behaviour change ships with a test. Bug fixes start with a failing test.
  • No reflection beyond record binding: no classpath scanning, no proxies.

Stage 1

Accept, then admit or refuse

  • One acceptor thread does nothing but accept(), so it is always ready for the next client.
  • A Semaphore(maxConnections) bounds open connections (default 1000). tryAcquire, never acquire: the accept loop must not block.
  • At the limit, the connection idle longest is closed to make room. Only if every connection is mid-request does the client get a fast 503.
  • The slot is released by a close callback that runs exactly once, wherever the connection ends.
jolt-core/.../in/jolt/Server.java, acceptLoop (trimmed)
while (!closing) {
    Socket socket = serverSocket.accept();
    if (!permits.tryAcquire() && !reclaimIdle()) {
        ConnectionHandler.reject(socket, config);   // 503 "Server busy", close
        continue;
    }
    var handler = new ConnectionHandler(socket, config, dispatcher,
            () -> closing, trusted, poller, this::release);
    live.add(handler);
    executor.execute(handler);                      // a new virtual thread
}

Say: v0.1 created a thread per connection and per request with no cap, so a flood killed the JVM (problem L2). The semaphore is the fix.
  • Follow-up "why 503 and not queue?": a fast refusal is better than making everyone slow; clients can retry.

Stage 2

Few OS threads, many connections

ThreadCountJob
Acceptor1 platformaccept() and admit
Poller1 platformWait for idle sockets with one Selector
Carriersabout one per coreRun all virtual threads
Handlervirtual, only while there is workParse, handle, write
  • A virtual thread that blocks on I/O frees its carrier, so blocking code scales.
  • Between requests a plain connection is parked in the poller: its thread ends, and a new one continues it when the socket is readable.
  • TLS connections keep waiting on their own thread, because an SSLSocket cannot be selected on.
jolt-core/.../internal/http/Poller.java, run loop
while (!closed) {
    register();                  // parked connections queued by handlers
    selector.select(tickMillis); // sleeps in epoll or equivalent
    collectReadable(woken);      // sockets that now have data
    expire();                    // close idle past keepAliveTimeout
    if (!woken.isEmpty()) {
        selector.selectNow();    // flush cancelled keys
        resume(woken);           // executor.execute(handler::resume)
        woken.clear();
    }
}
In the repo:Poller.javaADR 0026
Speaker notes
Say: I modelled the poller on Tomcat's NIO connector. Be honest about the value.
  • With virtual threads an idle connection was already cheap, so the gain over v0.4.1 is modest: timeouts in one place and reclaimable idle connections. It is not measured.
  • Tomcat benefits more because its workers are expensive OS threads in a fixed pool of 200.
  • Cost: more code, one more thread, and a connection is served by different virtual threads over its life.
  • The JDK picks the selector: epoll on Linux, kqueue on macOS, a wepoll layer on Windows (I confirmed WEPollSelectorImpl on my laptop).
Stage 3

One connection, many requests, strictly in order

  • Only one thread at a time works on a connection: read, handle, write, repeat. There is no shared response queue, so pipelined responses stay in order.
  • That removed two v0.1 bugs at once: the unsynchronised queue (L3) and the Thread.sleep(250) polling (L1).
  • Timeouts: keepAliveTimeout 5 s idle, readTimeout 10 s once a request starts, maxRequestsPerConnection 100.
  • SSE and WebSocket handlers keep the connection until they finish.
jolt-core/.../internal/http/ConnectionHandler.java, exchange (trimmed)
for (; served < config.maxRequestsPerConnection(); served++) {
    if (!ready) {                          // not just woken by the poller
        if (draining) return;
        if (poller != null && in.available() == 0) {
            poller.park(this);             // this thread ends here
            return;                        // poller calls resume() later
        }
    }
    socket.setSoTimeout(keepAliveTimeout);
    first = in.read();                     // timeout: close the idle connection
    socket.setSoTimeout(readTimeout);      // a request is arriving
    parsed = HttpParser.parse(in, limits, out);
    Response res = handle(parsed);
    ResponseWriter.write(out, res, keep, isHead);
}
In the repo:ConnectionHandler.java
Speaker notes
Say: ordering is guaranteed by construction, not by a lock: a single thread owns the connection at any moment.
  • Why in.available() == 0 before parking: bytes already read into the buffer would never wake the selector, so a pipelined request would hang.
  • HTTP/1.1 has no request ids, so responses must go out in request order (head-of-line blocking). HTTP/2 is not supported.
Stage 4

My own parser, with every limit on by default

  • Reads exactly Content-Length bytes, or a chunked body, in chunks (v0.1 truncated bodies: L7).
  • Rejects request-smuggling vectors, bare CR/LF, oversize lines, headers and bodies, with the right status.
  • Limits are plain config with safe defaults, so a naive app is still protected.

Stage 5

Middleware is a chain of responsibility

  • App.dispatch starts the chain; the last link is route resolution.
  • Each middleware gets (req, res, next). Calling next continues; not calling it stops the request.
  • Layers are matched by path prefix, so middleware can apply to part of the app, and routers can be mounted.
  • v0.1 ran only the first handler (L4); this is the fix.
jolt-core/.../in/jolt/App.java, dispatch
req.app(this);
res.request(req);
run(req, res, req.path(), () -> {
    String hint = Suggest.nearest(routes(), req.method(), req.path());
    throw new NoRoute("No route " + req.method() + " "
            + req.path() + (hint == null ? "" : ", did you mean " + hint + "?"));
});
jolt-core/.../in/jolt/Router.java, run and step
void run(Request req, Response res, String path, Middleware.Next done) {
    List<Middleware> chain = layers.stream()
            .filter(l -> matches(l.prefix, path))
            .map(Layer::middleware)
            .toList();
    step(chain, 0, req, res, path, done);
}

private void step(List<Middleware> chain, int i, Request req,
        Response res, String path, Middleware.Next done) {
    if (i < chain.size()) {
        chain.get(i).handle(req, res,
                () -> step(chain, i + 1, req, res, path, done));
    } else {
        mount(0, req, res, path, done);
    }
}

Speaker notes
Say: next is just a lambda that calls step with the next index: recursion instead of a loop, which is what lets a middleware run code both before and after the rest of the chain.
  • Order is registration order. The stock middleware (CORS, CSRF, rate limit, request id, sessions) are all this same interface.
Stage 6

Route lookup is a path trie

  • Segments are matched in this order: static, then constrained param (:id(\d+)), then plain :param, then *.
  • A constraint miss falls through to the next kind, so /users/me beats /users/:id.
  • No match: a 404 with a did-you-mean hint. A known path with another method: 405 with Allow. HEAD falls back to GET.
  • v0.1 looked routes up in static maps in registration order (L9, L14); the trie fixed precedence and made the library importable.
jolt-core/.../internal/routing/RouteTrie.java
/** Path trie with static segments, :param, :param(regex)
 *  and trailing :param? segments, and a trailing * wildcard.
 *  Precedence is static, then constrained param
 *  (registration order), then plain param, then wildcard;
 *  a constraint miss falls through. */
public final class RouteTrie<T> {
    private static final class Node<T> {
        final Map<String, Node<T>> statics = new HashMap<>();
        Node<T> param;
        List<Constrained<T>> constrained;
        T wildcard;
        T value;
        ...
    }
}

Speaker notes
Say: lookup walks one segment at a time, so cost depends on path depth, not on how many routes exist.
  • Insertion rejects bad patterns up front: wildcard must be last, no duplicate parameter names, malformed constraints.
  • Why a trie and not a list of regexes: precedence is explicit and cheap, and static segments are hash lookups.
Stage 7

Handlers stay one lambda; typed handlers do the binding

  • A plain handler is (req, res) -> ..., as in Express.
  • A typed handler binds path params and a JSON body into a Java record, calls your function, and turns the result (or a Reply) into a response.
  • A bad body is 400; a failed validation is 422. No reflection beyond record binding.
  • Parameters have types: req.param("id", Long.class).

Stage 8

Every failure becomes a response

  • Any throwable from the middleware or handler is caught in one place.
  • A registered onError mapper decides the reply; the mapper closest to the exception type wins.
  • An HttpException keeps its own status. Anything else becomes a generic 500 with no details; the stack trace goes to the logger only.
  • Headers set by middleware (CORS, cookies, security headers) survive on error replies. Optional problem+json bodies.
  • v0.1 left the connection hanging on an exception (L6). Now: no silent failure.

Stage 9

Writing the response, and when a handler keeps the connection

  • ResponseWriter serialises the status line, headers and body, and rejects CR/LF in header names and values (header injection).
  • The writer always sets the framing headers itself (Content-Length, Connection, Transfer-Encoding); a handler cannot, so it cannot produce a malformed message.
  • No body for 204, 304 and 1xx. HEAD responses carry headers only.
  • SSE, streams and WebSocket: the handler takes over the connection (taken) and keeps its thread until it returns.
  • StreamGuard applies an idle timeout (60 s default) and a maximum duration to taken connections.
  • A pub/sub Hub feeds SSE and WebSocket subscribers with bounded queues.

Speaker notes
Say: a taken connection leaves the normal request loop, so it is never parked in the poller; it ends when the handler returns.
  • Header injection: a value containing a newline could add a forged header, so the writer refuses it.

Proof app

BookMyShow, built on Jolt as a user would

  • A movie-ticketing app: browse a city's shows, hold seats, pay, webhooks, live seat updates over SSE.
  • It depends on Jolt only through the published artifact (JitPack). The upgrade to v0.4.2 has passed CI in a pull request.
  • Gaps I hit became Jolt issues, each with a workaround tracked in docs/JOLT_GAPS.md until fixed.
  • 563 tests pass against v0.4.2.
  • Layered, and enforced: domain imports only the JDK; application imports domain; web never imports adapters; an ArchitectureTest fails the build otherwise.
  • Two people must never get the same seat: a seat_lock table with primary key (show_id, seat_id) is the single guarantee, inside BEGIN IMMEDIATE SQLite transactions.
  • Money is stored in paise as long; time goes through Clock.

Honest limits

What it does not do, and what I would do next

  • HTTP/1.1 only. No HTTP/2, so head-of-line blocking applies to pipelined requests.
  • TLS is not selected on. The poller handles plain sockets; TLS connections wait on their own thread. Selecting on TLS needs an SSLEngine.
  • A hand-written parser. It needs heavy testing; Tomcat and Netty have years of fuzzing behind them.
  • Not on Maven Central yet: published through JitPack (issue #36).
  • The poller's gain is modest and unmeasured: virtual threads made idle connections cheap already.
  • Idle eviction is a linear scan of live connections, only when the limit is hit.
  • Idempotency refusals are written as plain text, not through the shared error path (issue #85).
  • Next: benchmark 0.4.1 against 0.4.2 on Linux, publish to Maven Central, and consider TLS through the poller.
